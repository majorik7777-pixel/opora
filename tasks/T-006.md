## Цель

Закрепить сквозной путь тестом и процессом: Playwright-сценарий «лендинг → онбординг → magic link → `/app`» на отдельной PGlite-БД и production-сборке, проверка мобильного 360 и доступности, CI, который прогоняет lint → typecheck → test → build → e2e.

## Контекст

Playwright-конфиг уже задаёт два проекта (desktop и mobile-360), порт `3100`, отдельную PGlite-БД `.data/e2e`, локально — Google Chrome, в CI — chromium (`tests/e2e/test-env.ts`). Проверка a11y — `@axe-core/playwright`. CI — GitHub Actions, кэш pnpm (`AGENTS.md §7`). Definition of Done требует e2e для UI-путей.

## Scope

- E2E-сценарий(ы): лендинг открывается → CTA → онбординг 5 шагов + согласия → `/auth` → dev-ссылка (при `AUTH_DEV_SHOW_LINK=true`) → verify → `/app`. Проверка, что `/app` недоступен без входа и что данные приветствия соответствуют онбордингу.
- Mobile-360 проект: критичные шаги без горизонтального скролла и с доступными тач-зонами.
- A11y: axe-проверки ключевых страниц (лендинг, онбординг, `/app`), фиксация нарушений и их устранение (или отдельная задача с обоснованием).
- `/api/health` — healthcheck для Playwright `webServer` и деплоя.
- CI workflow: checkout → pnpm/action-setup@v4 (pnpm 10) → setup-node@v4 (Node 22, cache pnpm) → `pnpm install --frozen-lockfile` → lint → typecheck → test → build → `playwright install --with-deps chromium` → `playwright test` с `CI=true`; concurrency-группа с отменой устаревших прогонов; артефакты отчётов при падении.
- Стабильность: детерминированные тестовые данные (e2e seeds), ожидания вместо sleep, повторные прогоны не должны зависеть от прошлого состояния (`.data/e2e` чистится).

## Out of scope

- E2E чата/дневника/программы/оплаты — в соответствующих задачах (T-101…T-104).
- Нагрузочные тесты, visual regression, кросс-браузерность (кроме chromium/Chrome), Safari/Firefox — позже.
- Аналитика, мониторинг, Sentry — позже.
- Деплой — runbook `docs/runbooks/deploy-backup.md`, не эта задача.

## Acceptance criteria

- [ ] `pnpm test:e2e` локально проходит (production build + Google Chrome), в том числе сценарий «лендинг → онбординг → magic link → `/app`».
- [ ] В CI прогон `playwright test` с chromium проходит на чистом окружении; повторные запуски стабильны (не менее 3 прогонов без флаков при разработке).
- [ ] Оба проекта Playwright выполняются: desktop и mobile-360; на 360 нет горизонтального скролла на ключевых экранах.
- [ ] axe: нет critical/serious нарушений на лендинге, онбординге и `/app` (или зафиксированное исключение с задачей).
- [ ] `/api/health` отвечает 200 и используется `webServer`.
- [ ] CI-workflow запускается на push/PR, кэширует pnpm, использует `--frozen-lockfile`, отменяет устаревшие прогоны через concurrency; при падении сохраняет Playwright-отчёт.
- [ ] E2E не требует внешних сервисов и реальных ключей: PGlite `.data/e2e`, `LLM_PROVIDER=fake`, `EMAIL_TRANSPORT=console`, `AUTH_DEV_SHOW_LINK=true` (см. `tests/e2e/test-env.ts`).
- [ ] В логах e2e нет реальных ПДн (только синтетические email); `.data/`, `test-results/`, `playwright-report/` не попадают в git.
- [ ] `pnpm verify` проходит; документы (`docs/DEFINITION_OF_DONE.md`, `README.md` при необходимости) отражают фактические команды.

## План работ

1. Healthcheck и стабильное e2e-окружение (чистая PGlite, env).
2. Сценарий сквозного пути + mobile-360 + axe.
3. CI-workflow (lint/typecheck/test/build/e2e, concurrency, кэш, артефакты).
4. Прогон `pnpm verify` и `pnpm test:e2e`; устранение флаков.

## Вопросы и допущения

- Локально Playwright использует установленный Chrome (`channel: "chrome"`), в CI — chromium из `playwright install --with-deps`; это уже зафиксировано в `playwright.config.ts`.
- На Phase 0–1 e2e покрывает один сквозной путь; расширение — в задачах функций.
- Если axe даёт нарушения в компонентах дизайн-системы, исправления идут в `@opora/ui` (согласовать write-scope).
