- **Зависимости:** T-004 (пользователь/сессия), T-005 (`/app`), T-101 (LLM-адаптер и промпт разбора)

- **Ссылки:** [`docs/planning/09-product-spec.md §6`](../docs/planning/09-product-spec.md), [`12-tech-plan.md §4`](../docs/planning/12-tech-plan.md), [`10-design.md §4.4`](../docs/planning/10-design.md), [`11-copy.md`](../docs/planning/11-copy.md), [`docs/adr/0003-auth-encryption-and-consents.md`](../docs/adr/0003-auth-encryption-and-consents.md)

## Цель

Дать пользовательнице дневник: быстрая запись настроения (1–10) и текста, теги, история по дням и бережный AI-разбор записи. Текст шифруется, данные не попадают в логи; AI-разбор — поддержка и рефлексия, не диагноз и не оценка личности.

## Контекст

Дневник — ядро продукта наравне с программой (`09-product-spec.md §6`): поля «дата, настроение 1–10, текст, голос (позже), теги, приватность», AI-разбор 2–4 предложения, история. Чувствительные данные — специальная категория ПДн: шифрование AES-256-GCM, логи без ПДн (ADR-0003). Дизайн — `10-design.md §4.4` (сверху настроение, поле текста, лента). Голос — после MVP.

## Scope

- `@opora/db`: `diary_entries` (`entry_date`, `mood` smallint 1–10, `text_enc` AES-256-GCM, `tags` text[], `created_at/updated_at`, `deleted_at` soft-delete); индексы по пользователю/дате; миграция.
- Контракт `@opora/shared`: zod-схемы создания/обновления записи, список тегов (`отношения`, `работа`, `тело`, `сон`, `другое`), ограничения длины текста, коды ошибок.
- `@opora/core/diary`: создание записи (настроение обязательно, текст опционален — запись «только настроение» допустима), чтение ленты по дням/курсором, чтение одной записи, мягкое удаление, проверка владельца; всё — через репозитории `@opora/db`.
- AI-разбор: промпт `diary.analyze.v1` в `@opora/llm`, вызов через адаптер; 2–4 предложения: что заметно, какой паттерн, что помогло; без диагнозов, оценок личности и обещаний; помечен в UI как «разбор AI»; не сохраняется как отдельная запись в Phase 1 (генерируется по запросу; если сохранять — отдельная миграция и решение).
- `apps/web`: `/app/diary` — форма записи (MoodPicker 1–10, текст, теги), кнопка «Разобрать с AI» (или авто-разбор после сохранения — по дизайну), лента записей по дням, экран записи, пустое состояние («мягкая подсказка»), загрузка/ошибки.
- Тесты: unit (валидация настроения 1–10, теги, шифрование/расшифровка), integration на PGlite (создание/лента/soft-delete/владелец), e2e (создать запись → увидеть в ленте; разбор на `fake`), мобильный 360, a11y.
- `docs/specs/diary.md` — контракт домена.

## Out of scope

- Голос/аудио и транскрибация (`DiaryAttachment`, `Transcription`) — после MVP (`09-product-spec.md §3`).
- Поиск, фильтры, экспорт — позже (требование экспорта данных — до публичного запуска, отдельной задачей).
- Недельные и финальные отчёты — T-103 (отчёт программы) и позже (недельный отчёт дневника).
- Напоминания о записи, стрик — позже (T-103/воркер).
- Аналитика событий — вне фазы.
- Редактирование записи старше текущего дня (политика хранения) — уточнить, в T-102 допускается редактирование своих записей.

## Acceptance criteria

- [ ] Запись создаётся: настроение 1–10 обязательно (вне диапазона → `VALIDATION`), текст опционален, теги из фиксированного списка; запись «только настроение» работает.
- [ ] Текст хранится только шифротекстом (`text_enc`); в логи, ошибки и телеметрию текст и настроение не попадают.
- [ ] Лента показывает записи пользователя по дням, только свои (проверка владельца на сервере); пустое состояние дружелюбное.
- [ ] AI-разбор: 2–4 предложения по записи через `@opora/llm` (`fake` в тестах), без медицинских формулировок и оценок личности; ошибка LLM не ломает сохранение записи (запись сохраняется, разбор можно повторить).
- [ ] Soft-delete: удалённая запись не показывается, данные не теряются физически до джоба анонимизации (позже).
- [ ] UI: форма удобна на 360 px (крупные тач-зоны), доступность (подписи, фокус, ошибки текстом), состояния loading/empty/error.
- [ ] `pnpm verify` и e2e проходят; `docs/specs/diary.md` создан и соответствует коду.
- [ ] Новые внешние зависимости/поля согласованы с интегратором; миграция не ломает существующие данные.

## План работ

1. Контракт `shared` + промпт `diary.analyze.v1` в `llm`.
2. Таблица и репозиторий дневника; миграция (интегратор).
3. Сервис `core/diary` + AI-разбор; тесты.
4. UI формы и ленты; состояния; 360/a11y.
5. E2E, `docs/specs/diary.md`, проверки.

## Вопросы и допущения

- Разбор AI не персистится в Phase 1 (генерируется по запросу) — в схеме `12-tech-plan.md` нет поля; если нужно хранить, отдельное решение и миграция.
- Один дневник на пользователя; приватность на уровне владельца, без шаринга.
- Редактирование/удаление записей — своё, в рамках T-102; политика «записи прошлых дней не редактируются» не вводится без решения.
- Голос — после MVP, отдельной задачей (вне T-102).
