# T-004. Magic-link auth и сессии

- **Статус:** review
- **Owner:** lead
- **Приоритет:** P0
- **Оценка:** 2–3 дня
- **Зависимости:** T-001, T-003
- **Write-scope:** `packages/core/src/auth/**`, `packages/core/src/session/**`, `packages/db/**` (только auth-репозитории), `apps/web/src/app/auth/**`, `apps/web/src/app/api/auth/**` (если используется route handler), `apps/web/src/lib/auth/**`, `apps/web/src/middleware.ts` (при необходимости), `packages/ui/**` (формы/сообщения), `packages/shared/**` — только интегратор, `tests/**`
- **Ссылки:** [`docs/adr/0003-auth-encryption-and-consents.md`](../docs/adr/0003-auth-encryption-and-consents.md), [`docs/specs/onboarding.md §4`](../docs/specs/onboarding.md), [`docs/planning/12-tech-plan.md §4, §11`](../docs/planning/12-tech-plan.md), [`docs/planning/09-product-spec.md §2`](../docs/planning/09-product-spec.md)

## Цель

Реализовать вход по magic link своими силами: запрос ссылки, dev-транспорт письма (консоль + показ ссылки в UI), verify с одноразовым токеном, серверные сессии в httpOnly cookie, сохранение онбординга после входа и закрытый `/app`.

## Контекст

Паролей и внешних auth-сервисов нет (ADR-0003). Токены и сессии хранятся в БД только хешами; cookie — `httpOnly`, `SameSite=Lax`, `secure` на https; TTL: magic link 20 минут, сессия 30 дней, черновик онбординга 60 минут. Лимит запросов — in-memory 5/мин/IP. UI-сообщения — по `11-copy.md` и тону проекта.

## Scope

- `@opora/core/auth`: `requestMagicLink(email, ip)`, `verifyMagicLink(token, ip)`, `logout(sessionToken)`, guard `getCurrentUser(sessionToken)`; генерация/хеширование токенов, проверка TTL и одноразовости, создание/отзыв сессии.
- Транспорт письма за интерфейсом: `console` (печать ссылки в лог) + опция `AUTH_DEV_SHOW_LINK=true` — dev-ссылка в ответе для UI; никаких секретов/токенов в production-логах (в dev — только dev-ссылка, это осознанное допущение).
- In-memory rate limit по `RATE_LIMITS` (`magicLinkPerIp`, `verifyPerIp`) с кодами `RATE_LIMITED`.
- `/auth`: форма email, состояние «проверь почту», повторная отправка, отображение dev-ссылки; verify-эндпоинт создаёт сессию, cookie `COOKIE_NAMES.session`, сохраняет онбординг из draft-cookie через `saveOnboarding` (T-003), удаляет draft-cookie, редиректит в `/app`.
- Guard: `/app` без сессии → `/auth`; сессия недействительна/истекла → `/auth`; выход очищает cookie и отзывает сессию.
- Тесты: unit (токены, TTL, одноразовость, rate limit), integration на PGlite (запрос → хеш в БД → verify → сессия), e2e-подготовка (полный сценарий — T-006).

## Out of scope

- SMTP/реальная отправка писем, шаблоны писем — позже (D-010 касается LLM, но принцип тот же: транспорт за интерфейсом).
- 2FA, роли, админка, OAuth/соцвходы — позже.
- Продление сессии/refresh-токены — не требуются в Phase 0–1.
- Восстановление доступа, смена email — позже.
- Rate limit на Redis — позже (сейчас in-memory, ограничение зафиксировано в ADR-0003).

## Acceptance criteria

- [ ] Запрос ссылки: email валидируется (`emailSchema`), письмо печатается в консоль, в БД лежит только `sha256`-хеш токена с TTL 20 минут.
- [ ] Dev-ссылка показывается в UI только при `AUTH_DEV_SHOW_LINK=true` и не показывается в production.
- [ ] Verify: одноразовый токен, истёкший/использованный даёт `TOKEN_EXPIRED`/`AUTH_INVALID`; успех создаёт сессию и httpOnly cookie (`SameSite=Lax`; `secure` при https).
- [ ] Сессия хранится в БД хешем, TTL 30 дней; выход отзывает сессию и очищает cookie; повторное использование украденного/отозванного токена не проходит.
- [ ] Онбординг из draft-cookie сохраняется ровно один раз; без черновика пользователь попадает в `/app` без онбординга (или на онбординг — по правилу T-005).
- [ ] `/app` без валидной сессии редиректит на `/auth`; серверные действия проверяют сессию, а не только UI.
- [ ] Rate limit: 6-й запрос в минуту с одного IP → `RATE_LIMITED` с понятным текстом.
- [ ] ПДн не в логах: email/токены не пишутся в логи приложения (кроме dev-ссылки в dev-режиме); ошибки — без раскрытия существования аккаунта.
- [ ] `pnpm verify` проходит; тесты auth в `pnpm test`; сквозной e2e — в T-006.
- [ ] Документы обновлены (ADR-0003 или `docs/specs/onboarding.md`), если детали отличаются от контракта.

## План работ

1. Репозитории auth-токенов/сессий в `@opora/db`; сервис в `@opora/core`.
2. Транспорт письма + dev-ссылка; rate limit.
3. `/auth` UI и server actions; verify route + cookie сессии.
4. Guard для `/app`; выход.
5. Интеграция с онбордингом (save после verify); тесты и проверки.

## Вопросы и допущения

- Имя cookie сессии — `COOKIE_NAMES.session` (`opora_session`); имя draft-cookie — `COOKIE_NAMES.onboardingDraft`.
- Анти-enumeration: на запрос ссылки всегда отвечаем одинаково, независимо от существования пользователя.
- In-memory rate limit сбрасывается при рестарте — принято для Phase 0–1, ограничение зафиксировано в ADR-0003.
- Dev-ссылка в UI — только для локальной разработки/e2e; тест на отсутствие в production-сборке (если возможно) — в T-006.
