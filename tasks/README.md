# Задачи «Опоры»: как вести

Версия 1.0 · 19.11.2026

`tasks/` — рабочая очередь проекта: каждая задача — отдельный markdown-файл `tasks/T-XXX.md`, самодостаточный для AI-агента. Файл задачи — источник правды по её содержанию; общий task board (если используется в мультиагентной сессии) — только для захвата и координации, при расхождении прав файл.

Связанные документы: [`AGENTS.md`](../AGENTS.md) (правила работы), [`docs/DEFINITION_OF_DONE.md`](../docs/DEFINITION_OF_DONE.md) (готовность), [`docs/planning/06-decision-log.md`](../docs/planning/06-decision-log.md) (решения).

---

## 1. Статусы

| Статус | Значение | Кто ставит |
|---|---|---|
| `planned` | Задача описана, можно брать. Зависимости должны быть `done` (или явно разрешены). | автор задачи |
| `in_progress` | Исполнитель взял задачу и работает. В шапке указан owner. | исполнитель |
| `review` | Реализация и проверки завершены, задача сдана на приёмку. Заполнен раздел «Отчёт». | исполнитель |
| `done` | Приёмка пройдена: acceptance-критерии подтверждены основателем/лидом. | **только основатель/лид** |

Правила статусов:

- Агент **не ставит `done` сам** — приёмку делает человек (основатель/лид); агент сдаёт в `review`.
- При возврате из `review` — статус снова `in_progress` и комментарий в отчёте: что исправить.
- Задача без acceptance-критериев не берётся: сначала дополни описание (или согласуй с основателем).
- Если задача не влезает в 3 дня — дели на части, каждая — отдельный файл.

## 2. Идентификаторы

| Диапазон | Что | Пример |
|---|---|---|
| `T-0xx` | Phase 0–1: каркас, лендинг, онбординг, auth, `/app`, e2e/CI | `T-001`…`T-006` |
| `T-1xx` | Следующие продуктовые задачи: чат, дневник, программа, оплата, safety | `T-101`…`T-105` |
| `T-2xx` | Инфраструктура, техдолг, аналитика, админка | по необходимости |

Номер не переиспользуется. Файл называется по id: `tasks/T-101.md`.

## 3. Один writer на файл и write-scope

- В каждый момент у файла один writer. Один агент не редактирует файлы, которые пишет другой.
- В шапке задачи указывается **write-scope** — список путей (файлов/каталогов), которые задача вправе менять. Всё вне scope — не трогать без согласования.
- `packages/shared/**` и миграции (`packages/db/migrations/**` или аналог) меняет только интегратор (основатель/лид) — даже если задача формально их касается (D-015, D-016).
- Если для задачи нужен файл вне scope — согласуй расширение scope в задаче (edit) и только потом меняй.
- Несколько задач не должны одновременно писать в один и тот же файл/каталог. Если пересечение неизбежно — задачи выполняются последовательно (зависимость).

## 4. Зависимости

- Поле `Зависимости` содержит id задач, которые должны быть `done` до старта (или `review` — если разрешена параллельная работа по контракту).
- Не начинай задачу с незавершёнными зависимостями: это ведёт к дублированию контрактов и конфликтам.
- Контракт-first: если двум задачам нужен общий тип/схема, сначала отдельная задача/правка контракта в `@opora/shared` через интегратора.

## 5. Формат файла

```markdown
# T-XXX. Короткое название

- **Статус:** planned | in_progress | review | done
- **Owner:** имя агента/человека (для planned — не назначен)
- **Приоритет:** P0 | P1 | P2
- **Оценка:** 1–3 дня
- **Зависимости:** T-XXX, T-YYY (или «—»)
- **Write-scope:** список путей
- **Ссылки:** planning-документы, ADR, спеки, связанные задачи

## Цель

Одно-два предложения: зачем задача и какой результат.

## Контекст

Коротко: что уже есть, на что опираемся, какие решения/ADR/спеки важны
(ссылки, а не пересказ всего).

## Scope

Что входит: функции, файлы/пакеты, контракты, тесты, документация.

## Out of scope

Что сознательно НЕ делаем в этой задаче (чтобы не расползался скоуп).

## Acceptance criteria

- [ ] Проверяемый критерий 1
- [ ] Проверяемый критерий 2
- [ ] `pnpm verify` проходит (и `pnpm test:e2e`, если менялся UI-путь)
- [ ] Обновлены `tasks/`, docs; при решении — ADR + D-XXX

## План работ

1. …
2. …

## Вопросы и допущения

Вопросы, которые нельзя решить самому; принятые допущения с обоснованием.

## Отчёт (заполняется при сдаче в review)

- Что сделано:
- Затронутые файлы:
- Прогнанные проверки:
- Допущения и открытые вопросы:
```

## 6. Как брать задачу

1. Найди задачу со статусом `planned`, зависимости которой закрыты.
2. В мультиагентной сессии — возьми её на общем task board (claim), затем в файле: статус `in_progress`, owner.
3. Прочитай задачу и связанные документы; если acceptance непонятен — задай вопрос основателю, не додумывай молча.
4. Работай вертикальным срезом: контракт → реализация → тесты → docs.
5. Перед сдачей проверь [`docs/DEFINITION_OF_DONE.md`](../docs/DEFINITION_OF_DONE.md), заполни «Отчёт», поставь `review`.

## 7. Правила содержания

- Задача — на русском, конкретно и проверяемо; без «сделать красиво» и «улучшить архитектуру».
- Acceptance — только то, что можно проверить (тест, сценарий, команда, скриншот на 360 px).
- Ссылки на planning-доки и ADR — обязательны, если задача меняет поведение/данные.
- ПДн: если задача касается чувствительных данных — requirement про шифрование и логи без ПДн включается в acceptance по умолчанию.
- Не выдумывай URL, метрики и «уже реализованное»: если чего-то нет — пиши «появится в T-XXX».
- После выполнения — обнови документы, которые задача изменила (`docs/specs`, `docs/prd.md`, `README.md`, `AGENTS.md` и т. п.).
