## Цель

Создать слой БД и онбординг: схему `users`, `auth_tokens`, `sessions_auth`, `consents`, `onboarding_answers` с миграциями и двумя драйверами (PGlite/PostgreSQL), сервис сохранения онбординга в `@opora/core` и UI 5 шагов с согласиями, который до входа хранит черновик в зашифрованной cookie.

## Контекст

Онбординг — первый сбор психологических данных, поэтому контракт жёсткий: значения из `packages/shared/src/onboarding.ts`, согласия из `ONBOARDING_CONSENT_COPY`, 18+ обязателен, ответы шифруются целиком, email — шифротекст + HMAC-отпечаток (ADR-0003). Dev-база — PGlite без Docker (ADR-0002). Поток guest → draft-cookie → magic-link → save → `/app` описан в `docs/specs/onboarding.md §4`.

## Scope

- `schema.ts` Drizzle: `users` (email-шифротекст + HMAC-отпечаток, `age_confirmed`, `status`, timestamps), `auth_tokens`, `sessions_auth` (хеш токена, TTL, `revoked_at`), `consents` (kind, version, accepted_at, ip_hash), `onboarding_answers` (связь с user, зашифрованный JSON, версия); индексы и уникальность (email-отпечаток, хеши токенов); id — UUID v7.
- Drizzle-конфиг (`packages/db/drizzle.config.ts`) и runtime-миграции: в Phase 0–1 — встроенный SQL-раннер `packages/db/src/migrations.ts` (идемпотентные стейтменты, учёт в `_opora_migrations`), применение при старте при `AUTO_MIGRATE=true` и через `pnpm db:migrate`; драйверы PGlite и `pg`; единый интерфейс `@opora/db`.
- `@opora/core`: сервис `saveOnboarding({ userId, answers, consents, ipHash })` — идемпотентная запись пользователя/согласий/ответов в транзакции; чтение онбординга для приветствия; репозитории без знания Next/React.
- Server actions: валидация ответов и согласий, сохранение draft-cookie (`sealJson`, TTL 60 мин), удаление cookie после сохранения; обработка ошибок по `ERROR_CODES`.
- UI `/onboarding`: 5 шагов из `ONBOARDING_STEPS`, прогресс, «Дальше» активна после выбора, согласия на последнем шаге, состояния loading/error, редирект на `/auth` после черновика.
- Тесты: unit на схемы/крипто-раундтрип и идемпотентность, integration на PGlite (миграции с нуля, сохранение, уникальность email, append-only согласий).

## Acceptance criteria

- [ ] Миграции применяются с нуля на PGlite и идемпотентны при повторном запуске; при `DATABASE_DRIVER=postgres` схема применяется к PostgreSQL 16 без изменений.
- [ ] `users` хранит email только шифротекстом, поиск — по HMAC-отпечатку; повторная регистрация того же email не создаёт дубль.
- [ ] `consents` пишутся отдельными строками `processing` и `special` с `CONSENT_VERSION`, `accepted_at`, `ip_hash`; повторная запись не перезаписывает историю.
- [ ] Ответы онбординга сохраняются зашифрованными целиком и читаются только сервером.
- [ ] Без трёх согласий сервер возвращает `VALIDATION` и ничего не пишет в БД.
- [ ] Черновик до входа живёт в зашифрованной cookie 60 минут; не теряется при переходе на `/auth`; не читается из JS.
- [ ] Сохранение идемпотентно: повторный вызов с тем же пользователем не создаёт дубликаты.
- [ ] UI: 5 шагов, прогресс, валидация, мобильный 360 px, доступность (клавиатура, фокус, подписи, ошибки текстом).
- [ ] `pnpm verify` проходит; integration-тесты на PGlite в `pnpm test`.
- [ ] `docs/specs/onboarding.md` обновлён, если имена полей/поведение отличаются от контракта; открытые вопросы — в отчёте.

## План работ

1. Схема Drizzle + миграции + драйверы PGlite/pg; проверка миграций с нуля.
2. Репозитории и сервис `saveOnboarding` в `@opora/core`; integration-тесты.
3. Server actions и draft-cookie; удаление cookie после сохранения.
4. UI 5 шагов и согласий на компонентах `@opora/ui`.
5. Проверки: `pnpm verify`, ручной сценарий, mobile-360.

## Вопросы и допущения

- Точные имена колонок фиксируются миграцией и обновляются в `docs/specs/onboarding.md` — расхождение документа и кода недопустимо.
- Пользователь создаётся **после** verify (T-004): до этого в БД нет ПДн, только зашифрованный черновик в cookie.
- Повторное прохождение онбординга существующим пользователем в Phase 0–1 не реализуется (не перезаписываем ответы).
- `citext` не используем (PGlite-совместимость): email-поиск по HMAC-отпечатку.
