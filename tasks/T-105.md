## Цель

Защитить пользовательницу в кризисном состоянии: до вызова LLM распознавать маркеры риска (суицид, самоповреждение, насилие, угроза жизни), останавливать обычный сценарий, показывать спокойный кризисный экран с 112 и проверенными контактами помощи, фиксировать событие **без содержания переписки** и ставить его в очередь на ручную проверку. Это не медицинская функция и не обещание «спасти» — это протокол безопасности и честные пределы возможностей.

## Контекст

Принципы: не медицина, не обещать результат, не обещать абсолютную конфиденциальность; при риске жизни — 112 и профильные контакты (`08-legal-pdn.md §6`, `09-product-spec.md §5.4`). Контекст СВО/утраты — табу в маркетинге и стоп-сценарий в чате (D-006): такие случаи не «продаём» и не разбираем упражнениями. Тексты кризисного экрана — `11-copy.md §9`. Без ML на старте: правила + словарь, затем (опционально) модельный классификатор (`12-tech-plan.md §7`). Логи — без текста сообщения.

## Scope

- `@opora/shared`: контракт `SafetyEvent`/`SafetyVerdict` (severity low/medium/high, категории: suicide, self_harm, violence, threat, other), `EMERGENCY_PHONE = "112"` (уже есть в константах); список горячих линий — только после проверки и утверждения (см. «Вопросы»), в коде не выдумывать номера.
- `@opora/core/safety`: классификатор на правилах — нормализация текста (регистр, ё/е, пробелы, обходные написания), regex/словарь по категориям, порог severity, защита от ложных срабатываний на безобидных фразах; интерфейс `checkBeforeGeneration(text, context)` → `SafetyVerdict`; интеграция в чат (T-101) и AI-разбор дневника (T-102): при риске **не вызывать LLM**, вернуть кризисный сценарий.
- Кризисный экран `/app/safety` (или модальный экран по дизайну `10-design.md §4.8`): спокойный фон, крупный текст «Ты не одна», кнопка «Позвонить 112», список горячих линий (после утверждения), кнопка «Я в безопасности» (возврат в приложение), подпись «Опора не заменяет экстренную помощь»; без анимаций; доступность и 360 px.
- `@opora/db`: `safety_events` (`user_id`, `severity`, `trigger` — категория/правило, **без текста**, `action`, `created_at`, `reviewed_at`, `reviewed_by`, `status` в очереди); миграция.
- Очередь: событие high-risk помечается для ручной проверки; в Phase 1 — запись в БД + пометка `needs_review` (админ-интерфейс — позже); при наличии — уведомление основателя по выбранному каналу (не через ПДн в тексте).
- Тесты: наборы фраз в репозитории — позитивные (должны срабатывать) и негативные (не должны: «убила время», «с ума схожу от работы» и т. п.); прогон в CI; интеграция с чатом (LLM не вызывается при риске), запись события без текста, экран доступен, кризисный экран не «ломает» сессию.
- `docs/specs/safety.md`: правила, категории, протокол, ответственные, список контактов со статусом проверки, пределы ответственности (проверить у юриста).

## Out of scope

- ML-классификатор и внешний moderation API — опционально позже; в T-105 — правила, при необходимости — модельный классификатор за флагом (решение).
- Автоматическое уведомление экстренных служб, отслеживание местоположения, звонки из приложения — не делаем.
- Полная админка безопасности (UI очереди, роли, SLA) — позже; сейчас таблица + статус.
- Круглосуточная модерация/дежурство — не обещаем; пределы честно описаны.
- Юридическое заключение по обязанностям и формулировкам — юрист (`08-legal-pdn.md §6`).

## Acceptance criteria

- [ ] Набор позитивных фраз (суицид, самоповреждение, насилие, угроза) срабатывает: LLM не вызывается, пользователь видит кризисный экран; в `safety_events` пишется категория/severity **без текста сообщения**.
- [ ] Набор негативных фраз не срабатывает (проверяется в CI, список расширяемый); ложные срабатывания разбираются с обоснованием.
- [ ] Кризисный экран: 112 доступен одной кнопкой, горячие линии отображаются только из утверждённого списка, есть «Я в безопасности» и дисклеймер; экран спокойный, без анимаций, доступен с клавиатуры и на 360 px.
- [ ] Тост/возврат в приложение после «Я в безопасности» корректен; сессия и данные не теряются, обычный чат после явного подтверждения не продолжает опасный сценарий автоматически.
- [ ] Интеграция с чатом и AI-разбором дневника: при риске не генерируются упражнения и «разбор»; дисклеймер доступен всегда.
- [ ] Логи и телеметрия без ПДн: никакого текста сообщений/записей, только id, категория, severity, код правила.
- [ ] Очередь: high-risk события помечены для ручной проверки; есть инструкция, что делать дежурному (docs), без обещаний пользователю круглосуточного ответа.
- [ ] `pnpm verify` и e2e (кризисный сценарий на тестовой фразе) проходят; `docs/specs/safety.md` создан и соответствует коду.
- [ ] Список контактов помощи утверждён основателем/юристом; до утверждения в UI только 112 и нейтральная формулировка, номера не выдумываются.
- [ ] Решение о списке горячих линий и пределах протокола зафиксировано в D-XXX/ADR (интегратор).

## Вопросы и допущения

- **Список горячих линий** в Phase 0–1 не утверждён: в коде — только `EMERGENCY_PHONE = "112"` и нейтральный текст; конкретные номера добавляются после проверки актуальности и утверждения основателем/юристом (не выдумывать).
- Протокол не гарантирует спасение жизни и не является экстренной службой — формулировки и пределы ответственности проверить у юриста (`08-legal-pdn.md §6`).
- «Я в безопасности» — пользовательское подтверждение, не медицинская оценка; повторные события фиксируются, но не блокируют приложение навсегда.
- Канал уведомления основателя о high-risk выбирается при реализации (email/Telegram) без текста переписки; конкретный канал — решение.
- Модельный классификатор — опционально и только после правил; при включении — отдельное решение (стоимость, задержка, ПДн).
