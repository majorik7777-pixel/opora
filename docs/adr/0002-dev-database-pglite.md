# ADR-0002. База данных: PostgreSQL в production, PGlite в dev/test

- **Статус:** принято
- **Дата:** 19.11.2026
- **Связанные документы:** `docs/planning/12-tech-plan.md §4, §11`, ADR-0001
- **Следствия для кода:** `packages/db`, `packages/shared/src/env.ts`, `apps/web/next.config.ts`, `tests/e2e/test-env.ts`, `.env.example`

---

## Контекст

Production-база проекта — **PostgreSQL 16 + Drizzle ORM** (тип `bytea`/`jsonb`, транзакции, миграции, привычный бэкап `pg_dump`). Но локальная среда — ноутбук основателя, где **нет Docker и локального PostgreSQL**; ставить и обслуживать их ради Phase 0–1 не хочется. E2E-тесты должны запускаться одной командой без внешних сервисов и без сети, а CI — не требовать отдельного сервис-контейнера и секретов.

При этом важно, чтобы dev, test и production использовали **один и тот же слой доступа к данным** (Drizzle-схема, миграции, репозитории) — иначе тесты перестают что-то доказывать, а расхождения диалектов всплывают в production.

## Решение

Production и любой «настоящий» стенд — **PostgreSQL 16** через `DATABASE_URL`, драйвер `pg`. Локальная разработка и e2e по умолчанию — **PGlite** (`@electric-sql/pglite`) — PostgreSQL, скомпилированный в WASM и работающий внутри процесса Node.js. Выбор — переменной `DATABASE_DRIVER`:

```
DATABASE_DRIVER=pglite | postgres
DATABASE_URL=postgres://...        # только для postgres
PGLITE_DATA_DIR=.data/dev          # только для pglite (каталог файлов, в .gitignore)
AUTO_MIGRATE=true                  # dev/e2e; в production false — миграции через pnpm db:migrate
```

Детали реализации:

- `packages/db` предоставляет единый интерфейс (схема, репозитории, миграции) и выбирает драйвер по `DATABASE_DRIVER`; `drizzle-orm` работает с обоими.
- В Phase 0–1 миграции — **встроенный SQL-раннер** в `packages/db/src/migrations.ts` (массив идемпотентных SQL-стейтментов, учёт в `_opora_migrations`), поэтому они применяются при старте приложения (dev/e2e при `AUTO_MIGRATE=true`) и в production отдельной командой `pnpm db:migrate` с production-`DATABASE_URL`. `drizzle-kit` (`pnpm db:generate`, конфиг `packages/db/drizzle.config.ts`) настроен для генерации SQL при развитии схемы; переход на файловый раннер — при росте схемы (T-101+).
- e2e использует **отдельную** PGlite-БД в `.data/e2e`; Playwright перед стартом сервера удаляет каталог (`rm -rf .data/e2e`), чтобы каждый прогон начинался с чистой схемы. Порт e2e — `3100`, чтобы не конфликтовать с dev.
- `@electric-sql/pglite`, `pg` и `drizzle-orm` вынесены в `serverExternalPackages` в `next.config.ts`: WASM-бинарник и нативный `pg` нельзя бандлить в серверный бандл Next.js.
- В `.env.example` по умолчанию `DATABASE_DRIVER=pglite`, `PGLITE_DATA_DIR=.data/dev`, `AUTO_MIGRATE=true`. `pnpm setup:dev` создаёт `.env` с теми же значениями.

## Альтернативы

| Вариант | Почему отвергнут (сейчас) |
|---|---|
| **Локальный PostgreSQL через Docker Compose** | У основателя нет Docker; это лишний шаг перед `pnpm dev` и причина «у меня не запускается». Compose сохранён в `infra/docker-compose.yml` для production-подобных проверок и деплоя — но не обязателен для разработки. |
| **SQLite (better-sqlite3/libsql)** | Другой диалект: нет `bytea`, `jsonb`, части Postgres-функций и семантики; тесты не проверяли бы production-путь, а миграции пришлось бы поддерживать в двух диалектах. |
| **Удалённая dev-БД в облаке** | Сеть, секреты, задержки, риск утечки тестовых данных и зависимость от доступности; не нужна для локального сквозного пути. |
| **pg-mem / эмуляторы** | Неполная эмуляция PostgreSQL, нестабильны на миграциях и типах — тесты давали бы ложную уверенность. |
| **Только Docker-контейнер в CI** | CI не должен требовать сервис-контейнера на Phase 0–1: e2e на PGlite быстрее и проще, а `build`/`test` не требуют внешней БД. |

## Ограничения и следствия

**Ограничения PGlite, которые нужно держать в голове:**

- **Один процесс, одно подключение.** PGlite работает в процессе Node.js и не рассчитан на несколько инстансов/воркеров одновременно. Поэтому в dev/e2e нельзя параллельно запускать несколько серверов на одной директории и воркер, который делит ту же БД. Для Phase 0–1 (лендинг, онбординг, auth, `/app`) этого достаточно; полноценный BullMQ-воркер и многопроцессная работа потребуют PostgreSQL.
- **Не для production.** Нет репликации, резервного копирования, мониторинга, конкурентного доступа и эксплуатационных гарантий. Production — только PostgreSQL 16.
- **Совместимость схемы.** Миграции и запросы должны оставаться переносимыми: не использовать расширения/фичи, которых нет в PGlite (например, не полагаться на `citext`; email ищется по HMAC-отпечатку, ADR-0003). Уникальные индексы, `jsonb`, `bytea`, транзакции — поддерживаются.
- **Производительность** dev/e2e ниже, чем у нативного PostgreSQL; для тестов это нормально, для нагрузочных проверок — нет.
- **Данные в `.data/`** — локальные, в `.gitignore`; PGlite-файлы нельзя коммитить и нельзя считать бэкапом.
- **`AUTO_MIGRATE`** в production должен быть выключен (`false`): миграции запускаются отдельно, осознанно, с бэкапом перед деплоем (см. `docs/runbooks/deploy-backup.md`).

**Как переключиться на PostgreSQL** (тоже способ проверить production-путь локально):

```bash
# infra/docker-compose.yml поднимает postgres:16-alpine на localhost:5432
docker compose -f infra/docker-compose.yml up -d postgres

# .env
DATABASE_DRIVER=postgres
DATABASE_URL=postgres://opora:...@localhost:5432/opora
AUTO_MIGRATE=false

pnpm db:migrate   # применить миграции
pnpm dev
```

**Следствия:** e2e/CI не требуют внешних сервисов; dev-запуск — одна команда; при появлении воркера или второго процесса в dev нужно будет либо согласованно останавливать их, либо временно переходить на PostgreSQL через compose. Решение пересматривается, если PGlite начнёт мешать (например, при фоновых задачах в разработке).
