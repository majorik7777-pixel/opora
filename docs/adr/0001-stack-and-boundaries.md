# ADR-0001. Стек и границы слоёв

- **Статус:** принято
- **Дата:** 19.11.2026
- **Связанные документы:** `docs/planning/06-decision-log.md` (D-015, D-016), `docs/planning/07-architecture.md`, `docs/planning/12-tech-plan.md`, `AGENTS.md §6`
- **Следствия для кода:** `pnpm-workspace.yaml`, `eslint.config.mjs`, `apps/web/next.config.ts`, `packages/*/package.json`

---

## Контекст

Проект «Опора» делает один основатель с помощью двух AI-харнесов (DeepSeek Harness и Hermes). Нужен один деплой, простой локальный запуск, жёсткие границы между доменами и возможность передавать контекст между агентами через репозиторий. Продукт — веб-сервис с формами, сессиями, чатом со стримингом и фоновыми задачами; нагрузки старта не требуют горизонтального масштабирования. Психологические данные — специальная категория ПДн, поэтому важно контролировать, где и как обрабатываются данные.

Ограничения: соло-разработка (нет команды, которая будет обслуживать много сервисов), скорый выход на сквозной путь «лендинг → онбординг → вход → главная», затем чат/дневник/программа/оплата. Микросервисы, отдельный API-сервер и тяжёлые клиентские SDK увеличивают стоимость владения без пользы на этом этапе.

## Решение

**Модульный монолит в pnpm-workspace.** Один git-репозиторий, один деплой веб-приложения, жёсткие границы пакетов:

```
apps/web        Next.js 15.5 (App Router), React 19 — UI, server actions, route handlers, позже /admin
apps/worker     BullMQ-каркас: напоминания, отчёты, сверка платежей (позже)
packages/core   домены: auth, onboarding, chat, memory, diary, programs, billing, safety, notifications
packages/db     схема Drizzle, миграции, репозитории; PGlite в dev/test, PostgreSQL 16 в production
packages/llm    адаптер LLM-провайдеров (fake | foreign | yandex | gigachat | cloudru)
packages/shared zod-схемы, константы, типы API, коды ошибок; серверные утилиты — в @opora/shared/server
packages/ui     дизайн-система (токены, компоненты), не знает доменов
infra/          docker-compose (PostgreSQL/Redis), Caddyfile, бэкапы
docs/           planning, adr, specs, runbooks, prd, DEFINITION_OF_DONE
tasks/          задачи для AI-агентов
tests/e2e       Playwright-сценарии и e2e-окружение
```

Стек: Next.js 15.5 + React 19 + TypeScript 5.9 (strict) + Tailwind CSS 4; PostgreSQL 16 + Drizzle ORM в production; PGlite (WASM PostgreSQL) как dev/test-драйвер (ADR-0002); magic-link auth своими силами (ADR-0003); BullMQ-каркас; ЮKassa — позже. Пакеты экспортируют исходный TypeScript (`main: ./src/index.ts`), Next транспилирует их через `transpilePackages`; отдельной сборки пакетов нет.

### Границы слоёв

| Слой | Правило | Проверка |
|---|---|---|
| `shared` | Нижний слой: zod, константы, типы. Никаких React/Next/`@opora/*`. Серверные утилиты (crypto, env, uuid) — только в `@opora/shared/server`. | ESLint `no-restricted-imports` |
| `core` | Домены. Не знает Next/React/UI/`apps/*`. Может использовать `shared`, `db`, zod. | ESLint |
| `db` | Схема, миграции, репозитории. Не знает домены, `llm`, UI, Next. | ESLint |
| `llm` | Транспортный слой: сообщения, роли, опции. Не знает домены, `db`, UI, Next. | ESLint |
| `ui` | Только React и стили. Не знает Next, домены, `db`, `llm`. | ESLint |
| `web` | Не ходит в БД напрямую — только через `@opora/core`. Запрещены `drizzle-orm`, `pg`, `@electric-sql/pglite`, `bullmq`, `@opora/worker`. | ESLint |
| `worker` | Без React/Next/UI; использует `core`/`db`/`shared`. | ESLint |

Правила зафиксированы в `eslint.config.mjs` (`no-restricted-imports` с объяснением для каждого пакета) и проверяются в CI. `packages/shared` и миграции меняет только интегратор (основатель/лид) — D-015, D-016.

### Почему server actions на Phase 0–1 и когда появится tRPC

На Phase 0–1 основные взаимодействия — формы: онбординг, magic-link вход, ошибки валидации. Server actions дают типизированный вызов серверной функции из формы без отдельного API-слоя, без клиентского рантайма и без сериализации URL/роутов; прогрессивное улучшение и редиректы работают из коробки. Этого достаточно для сквозного пути «лендинг → онбординг → `/app`».

tRPC появится, когда станет нужен полноценный клиентский слой: чат со стримингом (SSE), история сообщений с пагинацией, дневник с лентой и фильтрами, будущие мобильные клиенты/боты. Тогда типы API уже будут в `@opora/shared`, а tRPC-роутер станет тонкой обёрткой над `@opora/core` — это не потребует переписывания доменов. Стриминг чата делается route handler'ом с SSE (`/app/chat` или `/api/chat/stream`), вебхуки — REST (`POST /api/webhooks/yookassa`). Вводить tRPC «на всякий случай» раньше — лишняя зависимость и слой, который не проверен продуктом.

## Альтернативы

| Вариант | Почему отвергнут |
|---|---|
| **Микросервисы** (auth-сервис, chat-сервис, billing-сервис) | Соло-разработка: больше деплоев, коммуникации, наблюдаемости и конфигов без нагрузки, которая оправдала бы это. Границы доменов важны, но они достигаются структурой пакетов (D-015). |
| **Отдельный API-сервер** (Next.js только фронт) | Дублирование слоя типов и деплоя, CORS, вторая точка отказа; на Phase 0–1 нет клиентов кроме веба. Вернуться к вопросу, если появятся мобильное приложение/бот или потребуется независимый API — тогда выделять из `core`. |
| **Prisma вместо Drizzle** | Drizzle ближе к SQL и предсказуемым миграциям, хорошо типизирует запросы и поддерживает PGlite в одном слое с PostgreSQL (ADR-0002); миграции простые и читаемые. Prisma добавила бы отдельный движок и генерацию клиента; для соло-проекта это лишняя нетранспарентность. |
| **tRPC сразу** | На Phase 0–1 нет клиентского состояния, где tRPC окупается; server actions проще. tRPC вводится вместе с чатом/дневником, когда появляется реальный API-контракт. |
| **Отдельный auth-сервис/провайдер** (Clerk, Auth0, Supabase) | Внешний обработчик ПДн, трансграничная передача, стоимость и зависимость; magic-link + сессии своими силами закрывают потребность (ADR-0003). |
| **npm/yarn workspaces** | pnpm уже выбран: строгие зависимости, быстрый install, workspace-протокол, кэш в CI. |

## Следствия

- Контракт-first: сначала zod-схемы/типы в `@opora/shared`, затем реализация. Это снижает конфликты двух харнесов.
- Границы проверяются линтером на CI — нарушение импорта роняет сборку.
- Один деплой `apps/web`; воркер запускается отдельным процессом, но живёт в том же репозитории и использует те же пакеты.
- Пакеты не собираются отдельно: TypeScript-исходники транспилируются Next.js; для Vitest это тоже работает. Появится отдельная сборка — только если понадобится публикация пакетов или воркер вне pnpm-workspace.
- `packages/shared` и миграции — «узкое место» с одним writer'ом; изменения через задачи и интегратора.
- Возможная эволюция: выделение tRPC-роутера (чат/дневник), затем — при росте команды/нагрузки — выделение сервисов из `core` без переписывания доменов.
