# ADR-0003. Auth, шифрование и согласия

- **Статус:** принято
- **Дата:** 19.11.2026
- **Связанные документы:** `docs/planning/06-decision-log.md` (D-010, D-011), `docs/planning/08-legal-pdn.md`, `docs/planning/12-tech-plan.md §4, §11`, `docs/specs/onboarding.md`, ADR-0001
- **Следствия для кода:** `packages/shared/src/crypto.ts`, `packages/shared/src/auth.ts`, `packages/shared/src/constants.ts`, `packages/shared/src/env.ts`, `packages/core/src/auth.ts` (Phase 0–1)

---

## Контекст

Сервис обрабатывает психологические данные, которые по российскому праву относятся к специальной категории персональных данных (ст. 10 152-ФЗ): разговоры о состоянии, дневник, ответы онбординга. Нужны: хранение в РФ, отдельные согласия, 18+, шифрование, минимизация, отсутствие ПДн в логах. При этом в Phase 0–1 **нельзя** подключать внешние auth-сервисы и реальную отправку писем: это внешние обработчики ПДн, лишние зависимости и расходы, а магистраль продукта ещё не проверена. Auth должен быть простым, безопасным и заменяемым по деталям (SMTP, rate-limit на Redis) без переписывания домена.

## Решение

### 1. Вход по magic link, без паролей

- Пользователь вводит email на `/auth`; email нормализуется и валидируется zod-схемой `emailSchema` в `packages/shared/src/auth.ts`.
- Сервер генерирует случайный токен (`randomToken`, 32 случайных байта в base64url), сохраняет в `auth_tokens` **только `sha256`-хеш** токена и TTL 20 минут (`AUTH_TTL.magicLinkMinutes`). В открытом виде токен живёт только в ссылке.
- Ссылка ведёт на verify-эндпоинт: токен ищется по хешу, проверяется TTL и одноразовость (использованный токен помечается/удаляется). Затем создаётся сессия и выставляется cookie.
- Транспорт письма в Phase 0–1 — `EMAIL_TRANSPORT=console`: письмо печатается в консоль сервера. При `AUTH_DEV_SHOW_LINK=true` dev-ссылка показывается прямо в интерфейсе (только не в production). Реальный SMTP — позже, отдельной задачей; код отправки скрыт за транспортом, домен auth от него не зависит.
- Лимиты запроса ссылки — in-memory: 5 запросов/мин на IP и 20 verify/мин на IP (`RATE_LIMITS` в `@opora/shared`), чтобы не заспамить почту и не перебирать токены. Это осознанное упрощение Phase 1 (см. «Ограничения»).

### 2. Сессии — непрозрачные, в БД только хеш

- Сессия — случайный токен (`randomToken`), в БД (`sessions_auth`) хранится только `sha256`-хеш, TTL 30 дней (`AUTH_TTL.sessionDays`), есть `revoked_at` для выхода/отзыва.
- Cookie сессии: `httpOnly`, `SameSite=Lax`, `secure` при https; имя — `COOKIE_NAMES.session` (`opora_session`). JWT не используется: серверные сессии дают мгновенный отзыв и не зависят от размера/подписи клиентского токена.
- Проверка владельца и сессии — на сервере (в `core`/guard), не в UI. `/app` без валидной сессии редиректит на вход; после входа без завершённого онбординга — на онбординг.

### 3. Онбординг-черновик до входа

- Ответы онбординга и флаги согласий до появления пользователя в БД хранятся в **зашифрованной cookie** `opora_onboarding_draft` (`COOKIE_NAMES.onboardingDraft`), TTL 60 минут (`AUTH_TTL.onboardingDraftMinutes`).
- Шифрование — `sealJson`/`openJson` (AES-256-GCM, `@opora/shared/server`), поэтому содержимое cookie не читается в браузере и не попадает в открытом виде в логи прокси. После magic-link verify ответы сохраняются в БД, cookie удаляется.
- Отдельный TTL и отдельная cookie позволяют не создавать «пользователя-черновика» в БД и не хранить ПДн раньше времени.

### 4. Шифрование чувствительных полей

- AES-256-GCM на уровне приложения: `sealJson`/`openJson` (JSON), `sealText`/`openText` (строки), формат `iv (12 байт) + tag (16 байт) + ciphertext`, base64url. Ключ — `ENCRYPTION_KEY` из env: base64 ровно на 32 байта; проверка длины с подсказкой генерации (`openssl rand -base64 32`).
- **Email** хранится зашифрованным (`sealText`), а поиск пользователя идёт по HMAC-отпечатку (`hashEmail`) с `AUTH_SECRET` — одинаковый email даёт одинаковый отпечаток, но открытый email в БД не лежит.
- **Ответы онбординга** шифруются целиком (JSON-полезная нагрузка) — это психологические данные.
- **IP-адрес** не хранится в открытом виде: для согласий и rate-limit используется `hashIp` (HMAC-SHA256 с `AUTH_SECRET`). Полный IP нужен только на уровне сети/прокси и не попадает в БД приложения.
- Токены (magic link, сессии) — высокоэнтропийные, поэтому достаточно `sha256`, HMAC не требуется. HMAC/секрет нужен там, где значение предсказуемо или может быть перебран (email, IP).

### 5. Согласия и 18+

- Отдельные строки в `consents` для каждого вида: `processing` (обработка ПДн), `special` (специальная категория), зарезервированы `cross_border` и `marketing` (`consentKindSchema`), но в Phase 0–1 запрашиваются только `processing` и `special`.
- В каждой строке: `kind`, `version` (`CONSENT_VERSION = "2026-11-19"`, общий на текущую редакцию юридических текстов), `accepted_at`, `ip_hash`. Текст согласий — `ONBOARDING_CONSENT_COPY` в `@opora/shared` (единый источник для UI и записи).
- 18+ подтверждается чекбоксом в онбординге и сохраняется в пользователе (`age_confirmed`); без подтверждения пользователь не создаётся.
- Изменение текстов согласий/политики — новая `CONSENT_VERSION` и новая запись при следующем принятии; старые строки не перезаписываются (история согласий).

## Альтернативы

| Вариант | Почему отвергнут |
|---|---|
| **Пароли** | Дополнительная поверхность атаки (хеширование, сброс, брутфорс, утечки паролей), лишний UI и поддержка; для продукта без ценных аккаунтов magic link проще и безопаснее. |
| **Внешний auth-провайдер** (Clerk/Auth0/Supabase/Cognito) | Внешний обработчик специальной категории ПДн, вопросы локализации и трансграничной передачи (ст. 12/18 152-ФЗ), стоимость и зависимость; magic-link закрывает потребность. |
| **JWT-сессии в cookie** | Нельзя мгновенно отозвать сессию, токен крупнее, логика refresh усложняется. Серверные непрозрачные сессии с хешем в БД проще и безопаснее на этом масштабе. |
| **Хранить токены/сессии в открытом виде** | Утечка БД = готовые сессии и magic-link. Хеш в БД — стандартная практика; открытый токен — только в ссылке/браузере. |
| **Шифровать email с поиском по ciphertext** | AES-GCM рандомизирован (IV), одинаковые email дают разные шифротексты — точный поиск невозможен. HMAC-отпечаток решает это, не раскрывая email. |
| **Хранить IP в открытом виде** | ПДн, лишние данные и риски; для согласий/лимитов достаточно HMAC-хеша. |
| **Согласие одной строкой «на всё»** | Для специальной категории нужны отдельные согласия; «одним чекбоксом» — юридический риск. |

## Ограничения Phase 1

- **In-memory rate limit**: сбрасывается при рестарте, не работает при нескольких инстансах. Redis-лимитер — позже (когда появится Redis/воркер); интерфейс лимитера должен позволить замену.
- **Письма только в консоль**: SMTP и брендированные письма — позже; сброса пароля нет и не нужен, пока вход по ссылке.
- **Нет 2FA**: появится вместе с админкой (RBAC, 2FA — позже).
- **Нет согласия на трансграничную передачу**: в Phase 0–1 LLM-провайдер `fake`, данные не уходят; перед публичным запуском — контур РФ и полный пакет согласий (D-010, `08-legal-pdn.md`).
- **Ротация ключей**: смена `ENCRYPTION_KEY` сделает старые данные нечитаемыми без перешифровки; порядок ротации и перешифровки — отдельная задача до публичного запуска. `AUTH_SECRET` при смене меняет HMAC-отпечатки email/IP — потребуется миграция/поиск по старому секрету.
- **Потеря `ENCRYPTION_KEY` = потеря данных**; ключ хранится в менеджере секретов/бэкапе, вне репозитория.

## Следствия

- Все новые чувствительные поля проходят через `sealJson`/`sealText`; логи и аналитика не содержат их открытых значений.
- Email-поиск и защита от повторной регистрации — по HMAC-отпечатку; при смене `AUTH_SECRET` нужен план миграции.
- Согласия immutable (append-only), версия — часть записи; юридические тексты меняются вместе с `CONSENT_VERSION`.
- Детальный контракт онбординга и поток guest → draft-cookie → magic-link → save → `/app` — в [`docs/specs/onboarding.md`](../specs/onboarding.md).
