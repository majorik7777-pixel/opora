# Спецификация: онбординг

Версия 1.0 · 19.11.2026 · Статус: Phase 0–1 (T-003, T-004)

Контракт онбординга: шаги и значения, согласия, поток guest → draft-cookie → magic-link → save → `/app`, ошибки, что сохраняется в БД, критерии приёмки. Источники: `docs/planning/09-product-spec.md §2`, `10-design.md §4.2`, `11-copy.md §3`, ADR-0003. Код-контракт — [`packages/shared/src/onboarding.ts`](../../packages/shared/src/onboarding.ts) (единый источник значений для UI, zod-валидации и БД); при расхождении документа и кода прав код, документ обновляется.

---

## 1. Назначение

Онбординг — 5 вопросов за ~2 минуты, которые: (а) дают пользователю почувствовать, что сервис «про неё», (б) собирают минимум контекста для персонализации программы и AI-поддержки, (в) фиксируют обязательные согласия и 18+. Онбординг проходится **до входа**; вход нужен, чтобы сохранить ответы и создать аккаунт. Без согласий и подтверждения 18+ сохранение невозможно.

## 2. Шаги и значения

Один вопрос на экран; прогресс «Шаг N из 5»; кнопка «Дальше» активна только после выбора. На последнем шаге — согласия и кнопка «Начать». Тексты — `11-copy.md §3`; дизайн — карточки-варианты (RadioCard), крупные тач-зоны.

| # | id поля | Вопрос | Значения `value` → подпись (label) |
|---|---|---|---|
| 1 | `situation` | Что случилось? | `breakup` → Расстались; `divorce` → Развод; `affair` → Измена; `together_ended` → Отношения закончились, но мы вместе; `other` → Другое |
| 2 | `timing` | Как давно? | `under_week` → Меньше недели; `1_4_weeks` → 1–4 недели; `1_6_months` → 1–6 месяцев; `over_6_months` → Больше полугода; `over_year` → Год и больше |
| 3 | `pain` | Что болит сильнее всего? | `cant_let_go` → Не могу отпустить; `guilt` → Чувство вины; `anger` → Злость; `emptiness` → Пустота; `fear_alone` → Страх остаться одной |
| 4 | `goal` | Чего хочется? | `stop_thinking` → Перестать постоянно думать об этом; `recover_strength` → Вернуть себе силы; `understand_next` → Понять, что делать дальше; `be_heard` → Просто чтобы кто-то выслушал |
| 5 | `sleep` | Как ты спишь? | `ok` → Сплю нормально; `hard_fall_asleep` → Засыпаю с трудом; `wake_night` → Просыпаюсь ночью; `almost_none` → Почти не сплю |

Правила:

- Все пять полей **обязательны** (в `onboardingAnswersSchema` — непустые enum). UI не даёт перейти дальше без выбора, сервер повторно валидирует.
- Значения — стабильные строковые enum'ы (не UI-подписи): их можно хранить в БД и использовать в промптах/аналитике. Подписи меняются без миграции данных.
- Порядок и тексты берутся из `ONBOARDING_STEPS`; дублировать значения в UI-компонентах нельзя.
- Тексты не медицинские: «что болит», «как ты спишь» — про состояние, а не диагноз; в интерфейсе и письмах нет слов «диагноз», «лечение», «терапия» (D-012).
- Человекочитаемая подпись для приветствия и «что AI помнит» — `getOnboardingLabel(step, value)`.

## 3. Согласия и 18+

Перед кнопкой «Начать» — обязательные чекбоксы; тексты — `ONBOARDING_CONSENT_COPY` в `@opora/shared`:

| Ключ | Текст (источник) | Что записывается |
|---|---|---|
| `age` | «Мне 18+.» | `age_confirmed = true` у пользователя при сохранении онбординга; без него психологические данные не сохраняются и `/app` недоступен |
| `processing` | «Согласна с обработкой моих данных и политикой конфиденциальности. Это не медицинская услуга.» | строка `consents` с `kind = processing` |
| `special` | «Понимаю, что рассказываю о своём состоянии, и согласна на обработку этих данных для работы сервиса (ст. 10 152-ФЗ).» | строка `consents` с `kind = special` |

- `consentFlagsSchema` требует `literal(true)` для всех трёх флагов — частичное согласие невозможно.
- Виды согласий, зарезервированные на будущее: `cross_border`, `marketing` (`consentKindSchema`). В Phase 0–1 они **не запрашиваются**; появятся с трансграничкой/рассылками и отдельным решением.
- В каждой строке согласия: `kind`, `version` (`CONSENT_VERSION`, сейчас `2026-11-19`), `accepted_at`, `ip_hash` (HMAC, не открытый IP — ADR-0003).
- Изменение юридических текстов → новая `CONSENT_VERSION`; старые записи не перезаписываются.
- Ссылки на политику и согласие — рядом с чекбоксами; оферта и условия доступны из футера. Все страницы `/legal/*` открываются (черновики с пометкой «требует проверки юристом»).

## 4. Поток

```
/onboarding (гость)
  │  выбор 5 ответов + 3 согласия (только в состоянии клиента)
  ▼
server action (гость): валидировать → зашифровать → cookie opora_onboarding_draft (TTL 60 мин)
  │  (если пользователь уже вошёл — server action сразу сохраняет ответы в БД и ведёт в /app)
  ▼
/auth: email → magic link (письмо в консоль в dev; dev-ссылка при AUTH_DEV_SHOW_LINK)
  │
  ▼
verify-ссылка: проверить токен (sha256, TTL 20 мин, одноразовый)
  │  сессия: cookie opora_session (httpOnly/SameSite=Lax/secure), TTL 30 дней
  ▼
сохранить согласия + ответы онбординга из draft-cookie (идемпотентно)
  │  удалить draft-cookie
  ▼
/app (только при валидной сессии и завершённом онбординге)
```

Детали:

- **Гость** может пройти онбординг и уйти на `/auth`; ответы не теряются за счёт зашифрованной cookie. После verify cookie читается на сервере, расшифровывается, валидируется той же zod-схемой и сохраняется вместе с согласиями.
- **Черновик** — `sealJson({ answers, consents, acceptedAt })` (`onboardingDraftSchema`), имя cookie `COOKIE_NAMES.onboardingDraft`, `httpOnly`, TTL `AUTH_TTL.onboardingDraftMinutes` (60 минут). Значения в cookie не читаются из JS (шифротекст) и не логируются. Черновик пишется server action'ом при отправке последнего шага, а не на каждом шаге.
- **Уже вошедший пользователь** (например, повторно проходит онбординг): server action сохраняет ответы в БД сразу, без cookie, и ведёт в `/app`.
- **Пользователь создаётся при verify** (T-004), до сохранения онбординга. До сохранения ответов и согласий у него нет психологических данных, а `/app` недоступен — редирект на `/onboarding`.
- **Повторный вход** существующего пользователя с завершённым онбордингом: ответы не перезаписываются автоматически; `/app` открывается сразу.
- **Прямой заход на `/app`** без сессии → редирект на `/auth`; с сессией, но без онбординга → редирект на `/onboarding`.
- **Сессия истекла** (TTL 30 дней) → повторный magic-link вход; ответы онбординга уже в БД.

## 5. Что сохраняется в БД

Схема — `packages/db/src/schema.ts` (T-003); ниже — контракт в терминах таблиц и полей.

| Таблица | Что пишется из онбординга | Замечания |
|---|---|---|
| `users` | создаётся при verify (T-004): email (шифротекст `sealText`), HMAC-отпечаток email (`hashEmail`) для поиска, `status = active`, `created_at`; онбординг проставляет `age_confirmed = true` | один пользователь на email-отпечаток; открытого email в БД нет |
| `consents` | две строки: `processing` и `special`, `version = CONSENT_VERSION`, `accepted_at`, `ip_hash = hashIp(ip)` | append-only; уникальность `(user, kind, version)`; `id` — UUID v7 |
| `onboarding_answers` | JSON с пятью ответами (`situation`, `timing`, `pain`, `goal`, `sleep`), `version = ONBOARDING_VERSION`, зашифрован целиком (`answers_enc`), связь с user | психологические данные — только в шифротексте; читаются сервером через `openJson` |
| `auth_tokens` | создаётся в auth-потоке (T-004): хеш токена, TTL 20 мин, отметка использования | — |
| `sessions_auth` | создаётся в auth-потоке: хеш токена сессии, TTL 30 дней, `revoked_at` | — |

Инварианты:

- Психологические данные (ответы онбординга) не сохраняются без двух согласий и подтверждения 18+.
- Повторная обработка черновика идемпотентна: ответы обновляются (upsert по пользователю), согласия не дублируются за счёт уникальности `(user, kind, version)`.
- В логах и ошибках нет ни email, ни значений ответов — только id и коды ошибок.

## 6. Ошибки и состояния

Единый формат ошибок — `ActionResult` / `ERROR_CODES` (`@opora/shared/src/api.ts`). Тексты ошибок — тёплые, без вины («Похоже, в адресе опечатка», «Ссылка уже не действует — попроси новую»).

| Сценарий | Код/поведение | UI |
|---|---|---|
| Не выбран вариант на шаге | `VALIDATION` | «Выбери один вариант, чтобы продолжить» |
| Не отмечены все согласия | `VALIDATION` | подсветка чекбоксов, текст рядом |
| Повреждённая/истёкшая draft-cookie | вход не блокируется; черновик не сохраняется (warning в лог без содержимого) | пользователь попадает на `/onboarding` и проходит заново |
| Некорректный email | `VALIDATION` | «Похоже, в адресе опечатка» |
| Слишком частые запросы ссылки | `RATE_LIMITED` | «Ссылка уже отправлена. Попробуй через минуту» |
| Ссылка истекла (> 20 мин) или использована | `TOKEN_EXPIRED` / `AUTH_INVALID` | «Ссылка уже не действует — запроси новую» |
| Нет сессии на `/app` | редирект на `/auth` | — |
| Нет онбординга у пользователя | редирект на `/onboarding` | — |
| Внутренняя ошибка сохранения | `INTERNAL` | «Что-то сломалось. Попробуй ещё раз» + id ошибки в логах (без ПДн) |

Состояния экрана: выбранный вариант, «Дальше» disabled/loading, ошибка валидации, отправка письма (loading), «проверь почту» с возможностью отправить снова.

## 7. Аналитика

События `onboarding_start` и `onboarding_complete` зарезервированы в `12-tech-plan.md §10`, но аналитика **вне Phase 0–1** — в этом этапе не отправляются. Когда появится, свойства — только id/шаги/агрегаты, без ответов и текстов (не ПДн).

## 8. Критерии приёмки

- [ ] 5 шагов, прогресс 1/5…5/5; «Дальше» недоступна без выбора; назад не теряет выбор.
- [ ] Значения и подписи соответствуют `packages/shared/src/onboarding.ts`; дублей в UI нет.
- [ ] Без трёх согласий кнопка «Начать» не срабатывает; сервер повторно валидирует (`VALIDATION`).
- [ ] Ответы гостя сохраняются в зашифрованную httpOnly-cookie (60 мин) при отправке последнего шага и не теряются при переходе на `/auth` и обратно.
- [ ] Если пользователь уже вошёл, server action сохраняет ответы сразу, без cookie.
- [ ] После verify пользователь создан/найден, две строки согласий и ответы онбординга сохранены (если был черновик); draft-cookie удаляется.
- [ ] Повторный verify/повторная обработка не создаёт дубликатов; истёкшая ссылка даёт понятную ошибку.
- [ ] `/app` без сессии → `/auth`; с сессией без онбординга → `/onboarding`.
- [ ] Email/ответы не видны в открытом виде в БД и логах; IP только как хеш.
- [ ] Мобильный вид на 360 px, тач-зоны ≥ 44 px, фокус видим, ошибки текстом (a11y).
- [ ] E2E-сценарий «онбординг → magic link (dev) → /app» проходит (T-006).

## 9. Открытые вопросы

1. Финальные тексты согласий и политики — юрист (`08-legal-pdn.md`); до этого — черновики с пометкой.
2. Нужно ли отдельное согласие на трансграничную передачу до публичного запуска — зависит от LLM-провайдера (D-010, T-101).
3. Поведение при повторном прохождении онбординга пользователем с завершённым онбордингом: редактирование ответов из настроек — позже, отдельной задачей.
4. Схема онбординга реализована в `packages/db/src/schema.ts` (`onboarding_answers.answers_enc`, `version`, `completed_at`); при изменении схемы документ синхронизируется.
