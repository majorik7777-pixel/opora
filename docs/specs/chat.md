# Спецификация: чат

Версия 1.0 · 20.11.2026 · Статус: T-101 (каркас домена и UI)

Контракт чата: роли и лимиты, поток отправки, SSE-события, сборка контекста, safety-хук,
хранение и ошибки. Источники: `docs/planning/09-product-spec.md §5`, `12-tech-plan.md §6`,
`11-copy.md §7`, ADR-0001/0003, D-002 (чат — вспомогательный слой), D-007 (5 сообщений в день).
Код-контракт — [`packages/shared/src/chat.ts`](../../packages/shared/src/chat.ts); при расхождении
документа и кода прав код.

---

## 1. Назначение

Чат даёт «поговорить сейчас», когда человеку тяжело, но не заменяет программу и не превращается
в бесконечного компаньона: сервер считает дневной лимит, ответ ограничен форматом (3–5 предложений,
один вопрос в конце), кризисные сообщения останавливают генерацию и показывают телефоны помощи.

## 2. Поток отправки

```
POST /api/chat { text }
  → сессия (401, если нет)
  → валидация 1…2000 символов (400 VALIDATION)
  → тред пользователя (создаётся при первом сообщении)
  → дневной лимит по БД (429 RATE_LIMITED)
  → safety-хук ДО генерации
  → сохранение сообщения пользователя (content_enc)
  → сборка контекста
  → стриминг ответа провайдера
  → сохранение ответа (content_enc, provider)
```

Лимит проверяется только на сервере по таблице `chat_messages`: считаются сообщения с
`role = 'user'`, отправленные после начала текущего дня в `Europe/Moscow`. Подмена даты на клиенте
ничего не меняет.

## 3. SSE-события

`Content-Type: text/event-stream`, каждая строка — `data: <json>` + пустая строка.

| type | Поля | Что делает UI |
|---|---|---|
| `start` | `messageId`, `remaining` | запоминает id ответа, обновляет счётчик |
| `delta` | `delta` | дописывает текст в «печатающийся» пузырь |
| `safety` | `reason` | показывает кризисный блок с контактами, ответа не будет |
| `error` | `code`, `message` | показывает ошибку и кнопку повтора |
| `done` | `messageId`, `remaining` | переносит текст в историю, обновляет счётчик |

## 4. Контекст и память

- Системный промпт `chat.system.v1` (`packages/llm/src/prompts/chat-system.v1.ts`).
- Сводка онбординга: ситуация, срок, что болит, цель, сон.
- Последние 8 сообщений треда.
- Бюджет — 10 000 символов (~2 500 токенов). При переполнении отбрасываются самые старые
  сообщения; промпт и онбординг остаются всегда.
- Факты о пользователе (`memory_facts`) в T-101 не хранятся — точка расширения после T-102.

## 5. Безопасность и данные

- Текст сообщений хранится только в `chat_messages.content_enc` (AES-256-GCM, `sealText`).
- В логи, ошибки и телеметрию текст не попадает; провайдеру уходит только контекст запроса.
- `safety_flag`: `ok` | `risk`, выставляется хуком до генерации.
- Safety-хук в T-101 — локальный regex (`@opora/llm/safety`); модельный классификатор и кризисный
  экран — T-105. До T-105 чат нельзя открывать реальным пользователям.
- Тред один на пользователя; удаление аккаунта удаляет тред и сообщения (cascade).

## 6. Ошибки и состояния UI

| Ситуация | Ответ | UI |
|---|---|---|
| Нет сессии | 401 `AUTH_REQUIRED` | редирект на вход (страница требует онбординг) |
| Пустой текст / >2000 | 400 `VALIDATION` | текст ошибки под формой, ввод возвращается |
| Лимит исчерпан | 429 `RATE_LIMITED` | поле ввода недоступно, «лимит сбросится завтра» |
| Провайдер упал | событие `error` | сообщение + «Попробовать ещё раз» |
| Кризис | событие `safety` | блок с 112, МЧС, Красным Крестом |

## 7. Что осталось за рамками T-101

- Кризисный экран и полноценный протокол (T-105).
- Реальный провайдер РФ в production (пока `LLM_PROVIDER=fake` в тесте).
- Платный безлимит/токены (T-104), несколько тредов, удаление отдельных сообщений, голос.
- Метрики: события отправки/лимита/кризиса (T-305).
