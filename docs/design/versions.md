# Версии лендинга и откат

Правило: **каждая итерация лендинга — отдельный URL и отдельный git-тег.** Ничего не переписываем
поверх: текущая версия живёт на `/`, архивные — на `/1`, `/2`, …; в git — теги `landing-v1`, `landing-v2`.

## Что уже зафиксировано

| Версия | Дата | Где смотреть | Код | Тег |
|---|---|---|---|---|
| v1 | 20.11.2026 | `/1` | `apps/web/src/components/landing-v1/`, `apps/web/src/app/1/page.tsx` | `landing-v1` |

`/1` — это **копия компонентов**, а не ссылка на актуальные: правки текущего лендинга на неё не влияют.

## Как выпускать следующую версию (чек-лист)

1. **Скопировать текущее состояние в архив:** `cp -r apps/web/src/components/landing apps/web/src/components/landing-vN`
   (если версия ещё не скопирована) и добавить `apps/web/src/app/N/page.tsx` по образцу `/1`
   (`noindex`, canonical `/N`).
2. **Тег в git:** `git tag -a landing-vN -m "лендинг vN: <что изменилось>"` + `git push origin landing-vN`.
3. Править только `components/landing/*` и `/` — архив не трогать.
4. После правок: `pnpm verify`, e2e, скриншоты 360/1440, решение D-XXX в `docs/planning/06-decision-log.md`.
5. В таблицу выше добавить строку.

## Откат

- Быстро вернуть старую версию как основную: в `apps/web/src/app/page.tsx` направить импорты на
  `components/landing-vN` (или `redirect("/N")`, если нужен мгновенный откат без сборки).
- Полный откат кода: `git revert <commit>` (не `reset --hard`, чтобы сохранить историю) или checkout
  тега `landing-vN` в отдельную ветку.

## Почему так

A/B-сравнение требует, чтобы варианты жили одновременно; «фотография» прошлого помогает показать
динамику и не спорить о том, «стало ли лучше». Плюс `/N` не индексируется (`noindex`), поэтому
архивы не мешают SEO.
