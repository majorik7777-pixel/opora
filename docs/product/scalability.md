# Масштабируемость: много программ, один продукт

Дата: 20.11.2026 · Решение-основа: D-035 (одна платформа, много программ) · Статус: черновик к обсуждению

Вопрос: если программ станет несколько, они будут пересекаться по чату и дневнику — как не
превратить «Опору» в набор несвязанных лендингов и не переделывать всё на второй программе?

Ответ коротко: **программа — это контент и запись в каталоге, а не отдельный продукт.** Один бренд,
один домен, одна учётная запись, один чат, один дневник, одна аналитика. Программа подключается
к этому ядру как «курс» с параметрами.

---

## 1. Что является продуктом

| Слой | Что это | Меняется ли от программы к программе |
|---|---|---|
| Платформа | аккаунт, чат, дневник, оплата, safety, аналитика | нет, только контекст |
| Программа | 7 дней контента, практики, тон, промпт | да, целиком |
| Упаковка | лендинг программы, SEO-кластер, цена | да, но по шаблону |

Следствие: вторая программа = новый объект `ProgramContent` + строка в каталоге + SEO-кластер.
Никакого нового приложения, поддомена и второго аккаунта.

## 2. URL и навигация

```
/                              бренд-хаб: «с чем работаем» + все программы (с 2-й программы)
/programs/[slug]               страница программы: оффер, что внутри, цена, FAQ
/articles/[cluster]/[slug]     SEO-статьи, перелинкованные на программы
/app                           личный кабинет (noindex)
/app/program/[slug]            прохождение конкретной программы
/app/chat                      общий чат (контекст = активная программа)
/app/diary                     общий дневник (записи помечены программой/темой)
```

Правило переезда: пока программа одна, её оффер живёт на `/`. Когда появляется вторая —
`/` становится хабом, а лендинг первой переезжает на `/programs/rasstavanie` с **301**.
Это уже заложено в D-035 и `14-seo-platform.md`.

## 3. Данные: что общего, что раздельное

```
users            — один аккаунт на человека (без «аккаунт для тревоги»)
onboarding       — базовый профиль (кто, что случилось, цель) — общий
sessions         — общие
programs         — каталог: slug, название, статус, цена, версия контента
enrollments      — user × program: доступ, прогресс, текущий день (user_id+program_slug)
chat_threads     — один тред на пользователя; program_slug nullable = «о чём разговор»
chat_messages    — как сейчас + опциональная ссылка на программу из треда
diary_entries    — общие, с program_slug и тегами; один дневник, разные темы
entitlements     — доступ на программу + (позже) подписка «все программы»
safety_events    — общие, program_slug для аналитики
```

Ключевая мысль: **не дублировать чат и дневник на программу.** Человек не хочет второй дневник —
он хочет, чтобы «Опора» помнила контекст. Программа — это фокус разговора, а не отдельная комната.

Практически для T-101/T-102 это значит добавить `program_slug` (nullable) в `chat_threads` и
`diary_entries` сейчас, пока таблицы маленькие, — потом это миграция на живых данных.

## 4. ИИ-слой: один персонаж, разные промпты

- Промпт-регистр: `chat.system.v1` (база) + `program.rasstavanie.v1`, `program.anxiety.v1`.
  Сборка контекста: база → программа → онбординг → последние сообщения.
- Safety общий для всех программ: кризисный протокол нельзя «настраивать под продукт».
- Память: общий профиль (онбординг, устойчивые факты) + программа-специфичный контекст.
  Переход между программами не должен начинать «с чистого листа».
- Модель одна (адаптер `@opora/llm`), меняется конфигом.

## 5. Онбординг: базовый + микро

Сейчас 5 вопросов. При 3 программах спрашивать всё заново — зло. Схема:
1. Базовый онбординг при регистрации (5 вопросов, как сейчас).
2. При входе в новую программу — 2–3 вопроса именно про неё (что беспокоит, как давно, цель).
3. Ответы кладутся в общий профиль, второй раз не спрашиваем.

## 6. Монетизация при линейке

| Формат | Когда |
|---|---|
| 990 ₽ за программу | старт (сейчас) |
| Пакет «2 программы» 1 490 ₽ | после 2-й программы |
| Подписка 490 ₽/мес: все программы + безлимитный чат | когда есть 3+ программы и удержание |
| Апселл на финише: «следующая программа −50%» | сразу после отчёта 7 дней |

Доступ — `entitlements` на программу; подписка — отдельный тип доступа (`all_programs`).
Paywall один, меняется только список доступного.

## 7. SEO как отдельное направление

- Один домен, один sitemap, один набор целей в Метрике; программы не конкурируют за одни запросы,
  а покрывают разные кластеры (расставание / тревога / выгорание).
- Хаб-страницы: `/programs` (список), кластеры `/articles/[cluster]`.
- Каждая статья заканчивается CTA на конкретную программу — перелинковка решает, какая программа
  получит трафик.
- Контент-конвейер: бриф → черновик → AI-ревью по чек-листу → (позже) психолог → публикация.
  Сейчас — `.agents/skills/content-psychology-review/SKILL.md`.
- Технически: `/programs/[slug]` и `/articles/...` генерятся из данных, а не из ручных страниц.

## 8. Что сделать уже сейчас, чтобы не переделывать

1. `program_slug` в `chat_threads`, `diary_entries`, `entitlements`, `enrollments` (nullable).
2. Каталог программ: `programs` (slug, title, status, price, content_version) — даже если там одна
   строка.
3. `ProgramContent` уже параметризован — сохранить это правило: компоненты лендинга не знают тему.
4. Промпт-регистр с версией на программу.
5. События аналитики с параметром `program` (Метрика: параметры цели).
6. Роут `/app/program/[slug]` вместо `/app/program` (с редиректом для совместимости).
7. Sitemap и JSON-LD генерировать из каталога.

## 9. Антипаттерны (не делать)

- Отдельный поддомен/приложение под каждую тему — размывает бренд, душит SEO, удваивает поддержку.
- Второй аккаунт и второй дневник «для другой программы».
- Копия чата с другим системным промптом в другом месте кода.
- Разные платёжные интеграции под разные продукты.
- Своя аналитика на каждый лендинг.
