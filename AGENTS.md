# AGENTS.md — главный документ для любого AI-агента

Версия 1.0 · 19.11.2026 · Phase 0–1

Этот файл читает **любой** AI-агент (DeepSeek Harness, Hermes или другой), который продолжает работу над проектом. Он самодостаточен: здесь контекст продукта, жёсткие ограничения, карта репозитория, границы слоёв, команды, стиль и процесс. Планировочные документы — источник правды по продукту, этот файл — источник правды по инженерным правилам. Если правила расходятся — приоритет у `docs/planning/06-decision-log.md` и ADR; расхождение нужно зафиксировать, а не разрешать молча.

Начни с [`README.md`](README.md) (быстрый старт), затем [`docs/planning/README.md`](docs/planning/README.md) и документы в порядке чтения оттуда.

## 1. Что это за проект

«Опора» — автоматизированный онлайн-сервис психологической самопомощи для женщин 25–45 лет (ядро 28–40), РФ, 18+. Продукт: дневник, AI-собеседник и короткие 7-дневные программы; первая программа — «Пережить расставание». Монетизация по лестнице: бесплатный опыт (5 сообщений в день, первый день программы) → разовая программа 990 ₽ → позже подписка 490 ₽/мес. Канал продвижения — SEO, но приоритет сейчас — продукт, а не продвижение (D-019). Никакого ручного ведения клиентов: онбординг, программа, оплата и отчёты автоматизированы (D-001, D-008).

Технически это модульный монолит на pnpm-workspace: Next.js 15.5 (App Router) + React 19 + TypeScript 5.9 strict + Tailwind CSS 4, PostgreSQL 16 + Drizzle ORM в production и PGlite (WASM PostgreSQL) как dev/test-драйвер, magic-link auth своими силами, BullMQ-воркер как каркас. Без микросервисов, нативных приложений, Telegram-ботов и внешних auth-сервисов. Работают два AI-харнеса (DeepSeek Harness и Hermes) по одним артефактам в репозитории, поэтому документация и границы файлов — часть кода, а не «на потом».

## 6. Границы слоёв и правила импортов (ADR-0001)

| Слой | Может зависеть от | Запрещено | Проверка |
|---|---|---|---|
| `packages/shared` | только `zod` и stdlib | React/Next, `@opora/db`, `@opora/core`, `@opora/llm`, `@opora/ui`, node-модули в клиентском индексе | ESLint `no-restricted-imports` |
| `packages/core` | `@opora/shared`, `@opora/db`, `zod` | Next/React, UI, `apps/*` | ESLint |
| `packages/db` | `@opora/shared`, Drizzle, `pg`, PGlite | домены (`core`), `llm`, UI, Next, React | ESLint |
| `packages/llm` | stdlib/внешние SDK провайдера | домены (`core`, `db`), UI, Next, React | ESLint |
| `packages/ui` | React, `clsx`, `tailwind-merge` | Next, домены, `db`, `llm`, `apps/*` | ESLint |
| `apps/web` | `@opora/core`, `@opora/shared`, `@opora/ui` | прямые `drizzle-orm`, `pg`, `@electric-sql/pglite`, `bullmq`, `@opora/worker` | ESLint |
| `apps/worker` | `@opora/core`, `@opora/db`, `@opora/shared`, BullMQ | React/Next/UI, `apps/web` | ESLint |

Ключевые правила:

- **`apps/web` не ходит в БД напрямую** — только через `@opora/core`. Если нужен новый запрос, добавляй функцию в `core`, а не импорт драйвера в страницу.
- **`@opora/shared` — нижний слой.** Клиентский индекс (`@opora/shared`) не должен тянуть node: крипто и env живут в `@opora/shared/server` (`packages/shared/src/server.ts`), импортировать только из серверного кода.
- **`core` не знает Next/React/UI**, `llm` не знает доменов, `db` не знает доменов и UI.
- **Контракт-first:** сначала zod-схемы и типы в `shared`, потом реализация в `core`/`db`/`ui`. `packages/shared` и миграции меняет только интегратор.
- **Server actions на Phase 0–1** — для форм (онбординг, auth, позже дневник). Для чата со стримингом появится route handler с SSE; для богатого клиентского кэша и типобезопасного API — tRPC (когда именно — ADR-0001). Вебхуки — REST (`/api/webhooks/...`).

## 7. Команды и локальный запуск

Из корня репозитория (полный список — `README.md`):

```bash
pnpm install          # один раз, после клонирования
pnpm setup:dev        # создаёт корневой .env со случайными ключами
pnpm dev              # http://localhost:3000
pnpm lint             # ESLint, включая границы слоёв
pnpm typecheck        # tsc для инструментов и всех пакетов
pnpm test             # Vitest: unit/integration в пакетах
pnpm test:e2e         # build + Playwright: два проекта (desktop и mobile-360), порт 3100
pnpm verify           # lint + typecheck + test + build — обязательный минимум перед сдачей
pnpm build && pnpm start
pnpm db:generate      # сгенерировать SQL-миграцию Drizzle (интегратор; runtime-миграции Phase 0–1 — packages/db/src/migrations.ts)
pnpm db:migrate       # применить миграции к DATABASE_URL
```

Особенности окружения:

- **Env — только из корня.** Канонический `.env` — в корне; `pnpm setup:dev` создаёт симлинк `apps/web/.env → ../../.env`, потому что Next.js читает env-файлы относительно каталога приложения. `apps/web/next.config.ts` дополнительно вызывает `loadEnvConfig(repoRoot)`. Отдельный настоящий `apps/web/.env` не создаётся.
- **База в dev — PGlite:** файлы в `.data/dev`, миграции применяются лениво при первом обращении к БД при `AUTO_MIGRATE=true`. Docker/PostgreSQL локально не нужны (ADR-0002). Переключение на PostgreSQL: `DATABASE_DRIVER=postgres`, `DATABASE_URL=...`, `AUTO_MIGRATE=false`, `pnpm db:migrate`.
- **E2E** использует отдельную PGlite-БД `.data/e2e`, production-сборку и порт `3100`; локально Playwright запускает установленный Google Chrome, в CI — chromium из `playwright install`.
- **Не запускай `pnpm install` без необходимости** и не коммить изменения `pnpm-lock.yaml`, если задача их не требует. Не запускай `pnpm dev`/`pnpm build`, пока другой агент пишет код в тех же пакетах, — сначала согласуй.
- **CI** (`.github/workflows/ci.yml`): install --frozen-lockfile → lint → typecheck → test → build → playwright install chromium → e2e.

## 8. Стиль кода

- TypeScript strict; `any` запрещён (`@typescript-eslint/no-explicit-any: error`), неиспользуемые переменные — ошибка (исключение — префикс `_`).
- ESM (`"type": "module"`), именованные экспорты, без `default` там, где можно.
- Валидация на границах — только zod-схемы из `@opora/shared`; типы API не дублируются руками.
- Идентификаторы — UUID v7 (`@opora/shared/server` → `uuidv7`), время — UTC в БД.
- Ошибки — единый формат `ActionResult` / `ERROR_CODES` из `@opora/shared`; пользователю — человекочитаемый текст без вины и давления.
- **Крипто — только через `@opora/shared/server`:** `sealJson`/`openJson`, `sealText`/`openText` (AES-256-GCM), `sha256Hex`, `hmacHex`, `hashEmail`, `hashIp`, `randomToken`. Свои шифры и «временные» ключи не писать.
- **ПДн не попадают в логи, телеметрию, аналитику и сообщения об ошибках.** Логируем id, коды, латентность; текст переписки и дневника — никогда.
- Комментарии и документация — по-русски; имена в коде — по-английски.
- Новые чувствительные поля — шифровать на уровне приложения; новые внешние сервисы — за адаптером.

## 9. Стиль текстов и UI

- Язык интерфейса — русский, обращение **«ты»** (как в `11-copy.md`; альтернатива «вы» проверяется на аудитории, но менять без решения нельзя).
- Тон — тёплый, взрослый, спокойный, без осуждения и сюсюканья, без давления и таймеров, без чувства вины.
- Никакой медицины и обещаний результата: «поддержка», «самопомощь», «рефлексия», «программа», «дневник».
- Никакого военного/утратного контекста в маркетинге и текстах (D-006). Кризисные темы — протокол и контакты помощи, не «продукт».
- Дисклеймер о том, что сервис не медицинская услуга, и 18+ — на лендинге, в онбординге и в юридических страницах.
- **Мобайл-фёрст: проектируй с 360 px.** Один экран — одно действие; тач-зоны ≥ 44 px; контраст AA; видимый фокус; `prefers-reduced-motion`; масштабирование текста до 200% без поломок.
- Дизайн — по `docs/design/direction-v2.md` (D-033): прохладная бумага `#F1F1EA`, ink, мох, вино; Onest ведёт, Literata — «событие»; редакционная сетка, линии вместо карточек, без капс-бровей, `→`, стоковых фото людей и AI-генерации лиц. Перед UI-работой — скилл `.agents/skills/design-opora/SKILL.md`.
- У каждого экрана и компонента — состояния: default, hover, focus, disabled, loading, error, empty. Ошибки — текстом, не только цветом.

## 10. Как работать задачами

Подробный формат — [`tasks/README.md`](tasks/README.md). Кратко:

1. **Выбери задачу** из `tasks/` со статусом `planned` (для мультиагентной сессии — возьми её на общем task board, если он используется). Не начинай работу по задаче, которая зависит от незавершённых: сначала они.
2. **Поставь статус `in_progress`** и укажи owner в шапке файла задачи. Один writer на файл: не редактируй файлы вне write-scope задачи.
3. **Сделай вертикальный срез 1–3 дня:** контракт (`shared`) → реализация (`db`/`core`/`ui`/`web`) → тесты → docs. Если не хватает контракта, сначала согласуй его с интегратором.
4. **Проверь:** `pnpm verify`; для UI-путей — e2e; для чувствительных данных — шифрование и логи без ПДн.
5. **Сдай в `review`**, не в `done`: acceptance проверяет основатель/лид (приёмку делает человек, агент не сам себя принимает).
6. **Обнови документы:** статус задачи, `tasks/`, при решении — ADR и `D-XXX` в `06-decision-log.md`. Код без документов не считается готовым.

Правила, которые нельзя обходить:

- Один writer на файл; `packages/shared` и миграции — только интегратор (основатель/лид).
- Не меняй `package.json`, конфиги, чужие пакеты вне write-scope своей задачи — сначала согласуй.
- Если задача требует нового решения — предложи `D-XXX` в задаче, не правь `06-decision-log.md` сам.
- Если не уверен — пиши вопрос в файл задачи (`## Вопросы`) и продолжай по разумному допущению, зафиксировав его. Не выдумывай API, URL, метрики и «уже реализованное».

### 10.1. Чекпойнты для больших задач (обязательно)

Сервер 4 ГБ RAM. Один OOM-killer или перезапуск гейтвея рвёт ход агента, и всё, что не записано на диск, теряется (19–20.11 так оборвались две задачи). Поэтому задача, которая длится дольше ~20 минут или правит больше 5 файлов, ведётся так:

1. **Старт — чекпойнт.** В первой же пачке действий создать/обновить `HANDOFF.md` (или раздел `## Журнал` в файле задачи): цель, план из 3–7 шагов, какие файлы будут затронуты, как проверять.
2. **Чанки по 15–20 минут.** Один чанк = один проверяемый результат (страница, компонент, тест). После чанка дописать в `HANDOFF.md`: сделано / проверено (команда и её вывод) / дальше / на чём остановился.
3. **Состояние живёт на диске, не в переписке.** `HANDOFF.md` должен позволять продолжить работу, не перечитывая всю историю чата. Незакоммиченные правки — нормально; коммит WIP допустим, но без `--amend` и force.
4. **Браузер — по одному.** Chromium открывать только на время скриншота, один таб, закрывать сразу. Не держать браузер параллельно с `next build` / `pnpm verify`.
5. **Возобновление после обрыва:** сначала `HANDOFF.md`, потом `git status` / `git diff --stat`, и только потом код. Не переделывать то, что уже сделано.

## 11. Что считается готовым

Задача готова, когда выполнены acceptance-критерии задачи и чек-лист [`docs/DEFINITION_OF_DONE.md`](docs/DEFINITION_OF_DONE.md): сборка, линт, типы, тесты, e2e для UI-пути, ПДн не в логах, новые чувствительные поля зашифрованы, мобильный 360, доступность, пустые/загрузочные/ошибочные состояния, обновлены `tasks/`, при решении — ADR, docs обновлены.

## 13. Правила для второго харнеса (Hermes)

Hermes — второй исполнитель. Он работает по тем же артефактам и не рассчитывает на контекст чужого чата. Обязательный протокол:

1. **Прочитай** `AGENTS.md` → `README.md` → `docs/planning/README.md` и документы в указанном порядке → `tasks/`. Если документ противоречит коду — верь коду и зафиксируй расхождение в задаче.
2. **Возьми задачу** из `tasks/` (статус `planned`), поставь `in_progress` и owner `hermes`; в мультиагентной сессии — сначала task board, затем файл.
3. **Не трогай файлы вне write-scope задачи.** `packages/shared` и миграции меняет только интегратор (основатель/лид). Один writer на файл.
4. **Не меняй решения молча.** Новое решение — предложение `D-XXX` в задаче; интегратор вносит запись в `06-decision-log.md` и ADR. Планировочные документы без нового решения не редактируются.
5. **Git:** если репозиторий инициализирован — отдельная ветка/worktree на задачу (`feat/<task-id>`), без force-push в общие ветки; после merge — обновить статус задачи. Не коммить `.env`, `.data/`, `node_modules/`, артефакты тестов.
6. **Никаких реальных ПДн** в фикстурах, тестах, скриншотах и логах: только синтетические данные. Реальные ключи и доступы — никогда в репозиторий.
7. **Перед сдачей** — `pnpm verify` (и e2e для UI), затем статус `review` с отчётом в файле задачи: что сделано, какие файлы затронуты, какие проверки прогнаны, какие допущения и открытые вопросы.
8. **Ревью** делает другой агент/основатель; при расхождении ролей — меняются (D-016). Общение о работе — через артефакты в репозитории, а не через чат.
9. **Не начинай** SEO, рекламу, мобильные приложения, ботов, подписку и реальные платёжные/LLM-ключи, пока это явно не в задаче.
